# Девять слоёв одной системы

Маяк — учебная студия внедрения AI-систем примерно из 90 человек. В примере показаны пять ответственных. Цель — подготовить обоснованное предложение и оставить решение человеку. Интерфейс показывает каждый слой, а один сквозной процесс связывает их.

1. **Цели и люди.** Анна отвечает за финальный результат, Марк — за заявку, Ольга — за готовность внедрения, Ирина — за внутренние расчёты, Лев — за свои заявки. Критерии результата в `config/goals.yaml`.
2. **Роли и полномочия.** Роль определяет разрешения. Платформа проверяет их перед запуском и выдачей каждой записи. Марк видит цены, но не себестоимость. Ольга может получить справку, но не запустить коммерческое предложение. Лев не видит историю Марка. Анна видит историю команды и утверждает результаты.
3. **Знания и информация.** Markdown — обычный текст с заголовками. Frontmatter — блок свойств между `---`: владелец, дата, раздел и доступ. PostgreSQL хранит поисковую копию. Синхронизация проверяет все файлы, обновляет записи и удаляет отсутствующие. При ошибке старый индекс остаётся. Версия записи — SHA-256, отпечаток файла.
4. **Скиллы.** Скилл — сохранённый способ работы. `proposal` объявлен в манифесте агента и добавляется платформой в инструкцию модели. Версия метода записывается в запуск. `review` — инструкция человеку. Файл с методом не доказывает качество его исполнения. Деморежим не интерпретирует произвольные изменения инструкции.
5. **Агенты и модели.** `client-brief` собирает справку программой. `commercial-proposal` получает подбор и текст от модели, а цены считает кодом. Агент — отдельный HTTP-сервис. HTTP — способ обращения одной программы к другой. Модель — средство обработки текста, а не владелец полномочий.
6. **Инструменты и доступы.** Context API выдаёт разрешённые записи; LLM Gateway — единая точка обращения к модели. API — договорённый способ вызова функции другой программы. LLM — языковая модель. Ключ провайдера есть только у платформы. У агентов отдельные внутренние сети, нет сети базы, общего каталога знаний и выхода в интернет. Контейнер — изолированный процесс с подготовленной средой.
7. **Процессы.** Заявка → знания → выбор услуг → расчёт → текст → проверка → решение. Шаги описаны в `processes/proposal.md`, выполняются программой и человеком. Это один готовый процесс; универсального редактора графов здесь нет.
8. **Запуск и состояние.** Один запуск сохраняет вход, исполнителя, разрешённые источники с версиями, этапы, результат, время и оценку стоимости. Этапы — журнал действий, не скрытые рассуждения модели. Состояния: выполняется, ждёт проверки, одобрено, ошибка. `request_id` — идентификатор запроса: повтор возвращает прежний запуск. Исправления создают новые версии. После перезапуска прерванный вызов отмечается ошибкой; самостоятельного продолжения ещё нет.
9. **Проверка и улучшение.** Проверяем схемы, вычисления, доступ, повтор и решения. Человек читает результат и фактические источники. Подтверждённый вывод можно сохранить в памяти с автором, запуском и версией. Это не автоматическое обучение модели и не изменение базы знаний.

## Знания → поиск → ответ

RAG — поиск подходящих сведений перед ответом модели. Здесь он использует полнотекстовый поиск PostgreSQL с обработкой русских слов. Сначала отбираются разрешённые записи, затем выполняется поиск и ранжирование. В трассировке видны реально выданные записи и их версии. Фразы с другим смысловым выражением могут ничего не найти: векторного поиска пока нет. Если оснований недостаточно, уточняют запрос и источник; пустой поиск не заполняют выдуманным ответом.

Записи — небольшие самостоятельные документы. Длинные книги следует сначала разделить на разделы; отдельного конвейера PDF/OCR здесь нет. `updated` — дата, записанная владельцем, а не гарантия достоверности. Противоречивые данные должен разобрать владелец.

## Граница учебного режима

Переключатель «Смотреть как» показывает серверную фильтрацию для выбранной роли, но **не удостоверяет личность**. Демоверсия привязана к localhost и содержит только вымышленные данные. Личный токен позволяет проверить вход без переключателя; полноценный вход сотрудников, аудит администраторов и управление ключами — отдельная задача перед рабочим внедрением. Владелец компьютера и Docker имеет доступ к файлам и базе.

Токен агента — случайный временный пропуск, связанный с человеком, ролью, агентом и запуском. Его срок не больше 15 минут, после завершения он отключается. Он не даёт доступа к чужому запуску. Роль человека ограничивает разрешения даже если агент объявил более широкий список разделов.

Пользовательский API закрыт для соединений из контейнеров агентов: они обращаются только к внутренним точкам контекста и модели с токеном запуска. Платформа проверяет фактический адрес соединения, а сервер не доверяет подменённым proxy-заголовкам. Эта граница рассчитана на указанную схему Docker Compose. Для запуска чужого недоверенного кода или изменения сетевой схемы нужна отдельная проверка изоляции.

## Что не обещаем

- `docker compose up` запускает локальную учебную систему; это не подтверждение готовности корпоративного сервиса.
- Демонстрационный подбор — простые правила по ключевым словам, а не интеллект модели. Если ключевые слова не найдены, расчёт останавливается. Даже подобранную услугу проверяет человек.
- Соответствие JSON Schema проверяет формат. Оно не доказывает истинность текста и не исключает ошибку модели.
- Оценка стоимости по токенам не является счётом провайдера. Без настроенного тарифа показывается «не рассчитано».
- Нет отправки сообщений, покупок, расписания, автоматического принятия решений и реальных подключений к рабочим системам.
