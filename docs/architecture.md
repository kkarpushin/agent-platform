# Универсальная основа и первый процесс

«Маяк» — учебная рабочая среда. Девять слоёв задают устройство системы; поручение выбирает доступный способ работы. Общий исполнитель `work-assistant` применяет зарегистрированные текстовые скиллы. `task-intake` и `daily-brief` показывают конкретные процессы управления работой команды.

## Девять слоёв

1. **Цели и люди.** В `config/goals.yaml` — назначение и критерии; в `people.yaml` — сотрудники. Анна принимает изменения, Марк и Лев координируют проекты, Ольга отвечает за исполнение, Ирина — за финансовые сведения.
2. **Роли и полномочия.** Сервер проверяет роль перед запуском, выдачей знаний и принятием решения. Роль человека ограничивает агента и скилл. Учебные идентификаторы ceo/sales/delivery/finance отделены от русских названий.
3. **Знания и информация.** Markdown-файлы с метаданными загружаются в PostgreSQL. При поиске учитываются доступ человека и разделы агента. Синхронизация проверяет весь набор перед заменой; ошибочный файл не должен разрушить прежнюю базу. Версия — отпечаток содержимого, а не доказательство истинности.
4. **Скиллы.** Инструкции `execution: draft` доступны общему исполнителю после синхронизации. Он выбирает скилл по описанию либо использует явно выбранный, получает нужные разрешённые сведения и возвращает текст. Выбранная инструкция и её версия записываются в модельный вызов. `execution: instruction` — связанная инструкция агента или человека, не самостоятельное поручение.
5. **Агенты и модели.** Агент — отдельный HTTP-сервис с проверяемым входом и выходом. Модель вызывается через платформу и авторизованный CLI на компьютере владельца. Модель предлагает; код проверяет структуру, ID, источники и версии. Соответствие схеме не доказывает правильность смысла.
6. **Инструменты и доступы.** Агент получает временный пропуск только для своего запуска и роли, до 15 минут и не дольше выполнения. Доступны разрешённые методы знаний, состояния, скиллов и модели. Ключи входа в CLI остаются на компьютере; контейнеры агентов их не получают. Исполнитель забирает запросы по локальному API с отдельным секретом.
7. **Процессы.** Учебный цикл: сообщение → сведения проекта и текущие задачи → предложение → решение Анны → изменение общей задачи → последующее сообщение. Диспетчер может предложить соответствующий агент и вход; это ещё не запуск и не принятие. Новое внешнее действие требует отдельного инструмента и прав.
8. **Запуск и состояние.** Хранятся вход, автор, источники, инструкция, вызовы модели, результат и версии. Запуск и задача имеют разные статусы. Повтор request_id с тем же входом возвращает прежний запуск; другое содержимое даёт конфликт. Одно событие не должно применяться повторно. Обновление задачи требует совпадения её версии; история неизменна. Непринятое предложение можно разобрать повторно с явным замечанием и новым request_id; прежний результат сохраняется. Принятое действие продолжается новым событием.
9. **Проверка и улучшение.** Изолированные тесты проверяют поведение кода с контролируемыми ответами. Живой модельный запуск оценивают отдельно. Принятые решения и проверенные выводы сохраняются со ссылкой на результат. Память не обучает модель автоматически.

## Поиск перед ответом — RAG

Система получает разрешённые сведения до ответа модели. Поиск PostgreSQL работает по словам; для небольших разделов агент также читает разрешённые записи целиком. В журнале виден фактически выданный набор и версии. Это не векторный поиск и не гарантия понимания любой перефразировки.

Одна короткая запись — один Markdown-файл. Длинным документам потребуются деление на фрагменты и отдельная загрузка. Обновлённый файл становится виден приложению после синхронизации. Изменившийся источник блокирует новое принятие результата по прежнему основанию; исторические решения сохраняются. Полного механизма сроков действия и автоматического разрешения противоречий нет.

## Граница универсальности

Без изменения ядра добавляются знания, сотрудники с существующими ролями и текстовые скиллы общего исполнителя. Для новой программы, интеграции, вычислений или автоматического перехода нужны код, регистрация и проверки. Общий исполнитель создаёт ответ и предложение маршрута; он не запускает произвольные команды, не подключает сервисы и не принимает решения за пользователя.

В каркасе нет универсального редактора графов, круглосуточного расписания, внешней отправки и корпоративного входа. Для работы нужны приложение, исполнитель CLI, компьютер и сеть. Отказ модели не маскируется тестовым ответом. Стоимость подписочного обращения может быть неизвестна.

## Права и изоляция

«Смотреть как» демонстрирует роли, но не удостоверяет личность. Для реальных данных требуется корпоративная авторизация. Владелец машины и Docker имеет доступ к файлам и базе.

Каждый агент подключён к собственной внутренней сети; у него нет сети базы, каталогов знаний и выхода в интернет. Публичный API недоступен соединениям из контейнеров агентов: платформа проверяет фактический адрес, не доверяя proxy-заголовкам. Внутренние точки требуют временный токен. Эта защита рассчитана на приведённую схему Compose; запуск чужого недоверенного кода требует отдельной проверки.

CLI вызывается в пустой временной папке с отключёнными инструментами и пользовательскими подключениями. Это ограниченный исполнитель текстового запроса, а не полный интерактивный помощник с доступом ко всему проекту. Подробности и требования к версиям: [модель и доступ](model-and-access.md).
